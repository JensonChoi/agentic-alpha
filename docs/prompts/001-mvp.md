# Project Specification: Agentic Trading Benchmark Platform

## 1. Project Overview

Build a production-quality, open-source **agentic trading simulation and benchmarking platform** that compares passive investing, publicly disclosed celebrity/congressional trading strategies, deterministic momentum strategies, and LLM-powered trading agents.

The platform must be capable of running locally, support self-hosted LLMs, provide reproducible historical backtesting and forward paper-trading simulations, and expose an interactive dashboard for comparing investment performance and inspecting agent decisions.

The project should also support optional integration with **OpenClaw** through a custom skill.

**Critical requirement: This is strictly an educational and research-oriented simulation platform. It must never execute real-money trades or connect to live brokerage trading endpoints.**

The goal is not to guarantee investment profitability. Instead, the platform should enable rigorous experiments answering questions such as:

- Can LLM-assisted trading outperform buy-and-hold investing or deterministic strategies?
- Does a multi-agent architecture outperform a single-agent architecture?
- How does a self-hosted LLM compare against a cloud-hosted LLM?
- Does copying publicly disclosed congressional trades outperform passive investing after realistic reporting delays?
- Does additional agentic reasoning justify its computational cost?
- How do the approaches compare in risk-adjusted performance, reliability, and reproducibility?

Build the actual working application, not merely an architecture document or prototype mockup.

## 2. Non-Negotiable Safety Constraints

### 2.1 Simulation Only

The application must never trade real money.

Implement these constraints at the architectural level:

1. **Do not implement live brokerage execution or order submission APIs.**
2. Do not require brokerage credentials.
3. Do not include live-trading mode, environment variables, feature flags, or configuration switches that enable real-money execution.
4. All trades must be processed by an internal simulated execution engine.
5. Historical trades must use historical market prices.
6. Forward simulations must use market data but execute orders exclusively in a simulated portfolio ledger.
7. All displayed portfolio balances must be explicitly labeled as simulated.
8. Never allow an LLM to access real brokerage transaction functionality.
9. OpenClaw must interact only with the simulation backend.
10. Provide a persistent, visible **SIMULATION ONLY — NO REAL MONEY** label on the dashboard.

Use a simulated portfolio ledger as the single source of truth for cash, positions, transactions, and portfolio equity.

A market-data provider may supply quotes and historical prices, but it must not be used for trade execution.

### 2.2 Security

Treat market news, articles, filings, and other retrieved text as untrusted inputs.

- Defend against prompt injection.
- Validate all LLM-generated structured responses.
- Restrict agents to explicitly allowed tools.
- Never grant agents arbitrary shell or filesystem access.
- Store API credentials securely and never expose them to the frontend.
- Sanitize retrieved content before incorporating it into agent context.
- Apply timeouts, retries, and bounded budgets to tool calls.
- Enforce deterministic portfolio constraints independently of the LLM.
- Prevent duplicated scheduled runs from applying the same simulated trade twice.

## 5. Strategy Framework

Create a pluggable strategy framework.

All strategies must implement the same interface and operate on common market-data and portfolio abstractions.

Suggested Python contract:

```python
from typing import Protocol

class TradingStrategy(Protocol):
    async def generate_signals(
        self,
        context: MarketContext,
        portfolio: PortfolioState,
    ) -> list[TradeSignal]:
        ...
```

A `TradeSignal` should include:

```python
class TradeSignal(BaseModel):
    ticker: str
    action: Literal["BUY", "SELL", "HOLD"]
    target_weight: float | None
    confidence: float | None
    rationale: str
    strategy_id: str
```

Agent confidence is self-reported metadata, not a calibrated success probability.

Do not execute orders directly from strategy implementations.

All strategies submit proposals to the same simulated portfolio and execution engine.

### 5.1 Strategy A: VOO Buy-and-Hold

Implement a simple passive investment strategy:

- Start with configurable simulated capital.
- Allocate 100% to VOO at the beginning of the experiment.
- Hold throughout the simulation.
- Reinvest dividends when the selected accounting configuration specifies it.
- Track total return, cash, equity value, and drawdown.
- Support fractional shares for standardized benchmarking.

This is the primary benchmark.

Historical total-return calculations must handle dividends and splits without double-counting adjusted prices or cash distributions.

### 5.2 Strategy B: Congressional / Celebrity Copy Trading

Implement a strategy that simulates copying publicly disclosed trades.

For the MVP, prioritize congressional trading disclosures.

Support a configurable tracked person, initially using Nancy Pelosi's publicly disclosed family trading activity as an example.

Design the data-provider interface so other politicians or public disclosure datasets can be added later.

Requirements:

- Ingest publicly available transaction disclosures.
- Record the underlying transaction date.
- Record the public disclosure date and, where available, the precise publication timestamp.
- Identify purchase versus sale.
- Track the disclosed asset.
- Preserve the original reported value range.
- Deduplicate amended or repeated disclosures.
- Never assume the original transaction occurred at the disclosure date.

**Critical: Prevent look-ahead bias.**

The simulated portfolio can only react once the information was publicly available.

If the data contains a publication timestamp, schedule the trade for the first eligible simulated execution time after publication.

If only a disclosure date is available, use a conservative execution convention, such as the next trading day's open.

Never simulate copying a trade on its original transaction date in the realistic strategy.

Support configurable copying methods:

1. Equal-weight allocation across eligible disclosed purchases.
2. Fixed allocation per disclosed purchase.
3. Proportional approximation based on the midpoint of the reported transaction-value range.

Because transaction-size disclosures often contain ranges, explicitly label proportional allocation as an approximation.

For the initial MVP, prioritize equal-weight allocation.

A corresponding sell disclosure may reduce or close a tracked position according to a documented deterministic rule.

Handle cases in which the disclosure refers to options, private assets, or unsupported securities by skipping them with an explicit recorded reason. Never silently convert options into underlying-stock trades.

### Data acquisition

Create a provider abstraction capable of supporting:

- Quiver Quantitative or another authorized provider
- Public disclosure datasets
- Local CSV/Parquet imports

Do not assume all providers offer free historical API access.

If no authenticated source is configured, provide a documented sample dataset so the strategy remains demonstrable.

**Never fabricate historical disclosure records or label synthetic records as authentic.**

Include a data-provenance field and display it in the dashboard.

### 5.3 Strategy C: Rule-Based Momentum

Implement a deterministic momentum strategy.

Default example:

- Universe: configurable liquid US equities/ETFs.
- Use 20-day and 50-day simple moving averages.
- Generate bullish signals when the shorter moving average crosses above the longer moving average.
- Generate bearish signals when it crosses below.
- Maintain a configurable maximum number of holdings.
- Use equal weights for selected positions.
- Keep unallocated funds in simulated cash.
- Rebalance at a configurable frequency.

Avoid ambiguous crossover logic. Signals should depend only on completed bars available at the decision timestamp.

Use the next eligible trading session for simulated execution.

Allow configuration of:

- Moving-average windows
- Universe
- Rebalancing frequency
- Maximum positions
- Maximum allocation per security

Keep the initial implementation simple and deterministic.

### 5.4 Strategy D: Single-Agent LLM

Implement an LLM-assisted trading strategy.

The agent must not invent its own trading system.

Instead, it should evaluate predefined securities, indicators, market conditions, and available portfolio information to propose trades.

Available tools should include:

- Retrieve historical price data
- Retrieve technical indicators
- Retrieve current simulated positions
- Retrieve simulated cash balance
- Retrieve recent news when available
- Retrieve predefined fundamental metrics when available
- Retrieve the configured trading rules and limits

The agent should receive a bounded set of candidates generated by deterministic screening logic.

Example workflow:

1. Deterministic screener identifies potential trading candidates.
2. The LLM receives their indicators and supporting data.
3. The LLM evaluates the candidates.
4. The LLM produces structured trade proposals.
5. The deterministic risk validator reviews the proposals.
6. Accepted proposals are executed only in the simulator.
7. Decisions and supporting evidence are recorded.

Require structured JSON or equivalent validated Pydantic output.

Support:

- Local LLM through Ollama
- Remote OpenAI-compatible inference server
- Optional cloud model

Track the model identifier, inference configuration, token usage where available, latency, reasoning summary, and tool calls.

Do not store hidden chain-of-thought. Store concise decision rationales, explicit evidence, and tool traces instead.

### 5.5 Strategy E: Multi-Agent LLM

Implement a multi-agent trading strategy with four specialized roles.

**Technical Analyst**

Examines momentum, moving averages, volatility, and other configured quantitative indicators.

**Fundamental / News Analyst**

Examines available fundamental information, recent news, and contextual evidence.

If the necessary data is unavailable, explicitly report the missing information instead of fabricating an analysis.

**Risk Analyst**

Evaluates volatility, drawdown exposure, sector concentration, and proposed portfolio risk.

This is an advisory role only; deterministic risk controls remain authoritative.

**Portfolio Decision Agent**

Receives the analysts' structured recommendations, evaluates agreement and disagreement, and produces final trade proposals.

Run independent analyst agents concurrently where possible.

Use bounded timeouts and a configurable maximum number of model invocations.

The portfolio agent may be configured to use the same model as the analysts or a different model.

Record:

- Individual agent recommendations
- Agreement/disagreement
- Supporting evidence
- Final decision
- Number of model calls
- Latency
- Inference cost estimates

The multi-agent strategy must produce the same `TradeSignal` contract as the single-agent strategy.

### 5.6 Model Configurations

Allow separate experiment configurations such as:

```yaml

model:
  provider: ollama
  name: qwen3
  base_url: http://localhost:11434

trading:
  universe:
    - AAPL
    - MSFT
    - NVDA
    - AMZN
    - GOOGL
  initial_capital: 100000
  rebalance_frequency: weekly
  max_position_weight: 0.10
```

Model names are illustrative, not required defaults.

Validate model availability before starting an agent experiment.

Do not silently fall back from a configured local model to a paid cloud model.

## 6. Historical Backtesting Engine

Build a deterministic, event-driven backtesting engine.

It should support:

- Configurable start and end dates
- Configurable starting capital
- Daily OHLCV market data
- Market calendars and non-trading days
- Corporate-action adjustments
- Cash balances
- Fractional share simulation
- Transaction costs
- Slippage
- Simulated order fills
- Portfolio equity snapshots
- Position history
- Rebalancing
- Trade history

For the MVP, focus on long-only US equities and ETFs.

Do not implement short selling, leverage, margin, options trading, or derivatives execution.

Use daily-frequency strategies initially.

### 6.1 Execution Timing

Enforce realistic event ordering:

1. Market data becomes available.
2. Strategy generates a decision.
3. Risk engine validates proposals.
4. Simulator schedules orders.
5. Orders fill at the next eligible execution event.
6. Portfolio ledger is updated.

Avoid using the same day's closing price to make a decision and then filling at that already-observed close.

A simple default is:

- Signals generated after the completed daily bar.
- Orders filled at the following eligible market open.
- Configurable slippage and transaction costs.

If the next day's opening price is unavailable, record the order as unfilled rather than inventing a price.

### 6.2 Point-in-Time Integrity

Prevent look-ahead bias.

At any simulated timestamp, strategies must only access information available at or before that timestamp.

For data types other than market prices, distinguish:

- Event date
- Source publication timestamp
- Ingestion timestamp
- Effective availability timestamp

Historical news and fundamentals must only be exposed to agents if the system can establish that the information was available at the historical decision time.

If point-in-time news or fundamentals are unavailable, either disable those tools for historical experiments or mark the experiment as non-comparable.

Do not let historical LLM backtests retrieve contemporary web results.

Document that model pretraining may still contain future knowledge and cannot be fully corrected by application-level timestamp filtering.

### 6.3 Data Quality

Handle:

- Missing price bars
- Delisted securities where supported by the source
- Splits
- Dividends
- Stale securities
- Symbol changes
- Market holidays
- Survivorship bias

Do not forward-fill missing execution prices.

Clearly distinguish total-return and price-return calculations.

Record data-provider provenance and dataset versions.

## 7. Forward Paper-Trading Simulator

Implement a forward simulation mode that uses newly available market data to make decisions while maintaining an entirely fictitious portfolio.

This should not rely on broker paper-trading accounts.

Use the application's own ledger and execution simulator.

Features:

- Configurable virtual starting capital
- Daily or scheduled strategy evaluation
- Persistent virtual portfolio balances
- Simulated orders and fills
- Transaction history
- Equity snapshots
- Strategy performance
- Restart recovery
- Duplicate-execution prevention

Use market-data timestamps to determine whether information is sufficiently fresh.

If no new valid market data is available, skip execution and record why.

A scheduler may trigger analysis runs, but execution must remain simulation-only.

Never issue real orders.

## 8. Shared Risk Management

Build a deterministic risk engine that cannot be bypassed by strategy output.

Default constraints:

```yaml
risk:
  max_position_weight: 0.10
  max_total_exposure: 1.00
  allow_short_selling: false
  allow_leverage: false
  allow_margin: false
  allow_options: false
  minimum_cash_balance: 0
```

The engine should validate:

- Supported symbol
- Order direction
- Portfolio cash availability
- Maximum position size
- Maximum total invested exposure
- Valid market price
- Duplicate order requests
- Nonnegative portfolio balances
- Portfolio accounting invariants

If a signal violates a constraint, reject it or deterministically resize it according to documented configuration.

Record every rejected or modified proposal and its reason.

Some baseline strategies, such as VOO buy-and-hold, legitimately require 100% exposure to one ETF. Allow strategy-specific allocation profiles while maintaining the same accounting and execution semantics.

Clearly disclose differing risk budgets in comparisons.

## 15. Testing Requirements

Implement automated tests for the core trading logic.

At minimum include:

### Portfolio Accounting

- Buy reduces cash and increases position size.
- Sell increases cash and reduces position size.
- Portfolio value equals cash plus market value of holdings.
- Fees affect simulated balances correctly.
- Fractional shares are handled consistently.
- Splits and dividends are accounted for correctly.
- Duplicate fills cannot be applied twice.

### Backtesting

- No same-bar look-ahead execution.
- Historical data cannot be accessed before its availability timestamp.
- No execution on market holidays.
- No fill with missing or invalid prices.
- Orders execute at configured eligible events.

### Celebrity Copy Trading

- Disclosure date is respected.
- Original transaction date does not become the simulated execution date.
- Duplicate disclosures are ignored.
- Unsupported security types are skipped.
- No fabricated trades are introduced.

### Momentum

- Moving averages calculate correctly.
- Crossover detection works.
- Insufficient history prevents signals.
- Rebalancing respects allocation constraints.

### LLM Agents

- Malformed model output is rejected.
- Tool-call budgets are enforced.
- Model timeouts are handled.
- Unavailable tools do not produce fabricated data.
- Agent outputs cannot bypass the risk engine.
- Local-model configurations do not automatically invoke cloud APIs.

### Simulation-Only Guarantees

- No live brokerage order APIs are present.
- The application starts without brokerage credentials.
- No real order route can be enabled through configuration.
- OpenClaw exposes only simulation operations.
- The simulated ledger is the only source of portfolio balances.

Use deterministic fixtures so most tests do not require network access or LLM inference.

## 21. Engineering Expectations

Use sound software engineering practices throughout.

- Prefer clear abstractions over overly complicated frameworks.
- Use type annotations consistently.
- Avoid duplicated business logic.
- Keep financial calculations deterministic and independently testable.
- Clearly separate simulated orders from trade proposals.
- Version experiment configurations.
- Make errors observable.
- Preserve reproducibility.
- Avoid unnecessary external dependencies.
- Do not hardcode model names, trading symbols, API credentials, or database URLs.
- Make the application extensible without requiring fundamental architectural changes.

When implementation choices are ambiguous, select the simplest technically sound solution that preserves the core research and benchmarking objectives.

Prioritize correctness of market-data timing, portfolio accounting, risk constraints, and experiment reproducibility over visual polish or additional strategy features.

**The final result should be a working, self-hostable agentic trading simulation platform—not a real-money trading system.**
